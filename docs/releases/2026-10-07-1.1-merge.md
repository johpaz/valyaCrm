## What shipped
- New endpoint `POST /api/v1/crm/vendedores/identificar`: takes a phone number in
  E.164 format and returns the rep's `vendedorId`, `nombre` and `rol`. It reuses
  the WhatsApp path's phone lookup (`buscarVendedorPorTelefono`), which now also
  selects `rol`.
- The endpoint is listed under "Current API endpoints" in `valyaCrm/CLAUDE.md`.

## Acceptance criteria status
1. Active rep's phone returns 200 with `vendedorId`, name and role — Met
2. Unknown phone returns 404 with a clear message — Met
3. Missing or empty phone returns 400, no crash — Met (four shapes checked)
4. Inactive rep's phone returns 404 — Met
5. Response gives the frontend what rep-scoped calls need — Met
6. Spanish naming, mounted under `/api/v1/crm` — Met

All verified manually against the running backend; `valyaCrm` has no test suite.

## Known issues and tech debt
From the PR's review (verdict AMBER, no blocking findings):
- Hand-built responses are labelled `text/plain`, not `application/json`. Same
  for the existing `POST /vendedores`. Frontend callers must parse the body
  regardless of content type.
- The phone number is written to the application log in clear text on every
  call (pre-existing logging, now reachable from a public endpoint).
- No auth, no rate limit and open CORS make rep identities enumerable by phone
  number. Accepted for the beta (decision 1); revisit before production.
- 500 responses return the internal error message to the caller (existing
  repo pattern).
- No automated tests; the change touches a function on the live WhatsApp path.
- `bun run lint` is broken repo-wide (no ESLint config). Pre-existing.
- `vendedorModel` requires a plain-text `contrasena` that nothing reads; this
  affects 1.3 (admin add-salesperson).
- Two throwaway test reps remain in the database, by PM decision.
