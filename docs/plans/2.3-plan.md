Plan: Update an opportunity's stage
ID: 2.3
Date: 2026-10-09
Round: 1
Goal: Add `PATCH /api/v1/crm/oportunidades/:id/estado` so moving a deal to a
new stage in the UI saves in the backend, and make every opportunity update
refresh its update date so the 2.1 list order is right.

## Out of scope
- Changing any other field through this endpoint; wiring the UI (2.6, 2.7);
  authentication.

## PM decision (2026-10-09): option A for the update date
2.1 sorts by `fechaActualizacion`, which today never changes after creation:
all three update paths (the stage update the agent and this endpoint share,
adding an activity, closing a won deal) use `findByIdAndUpdate`, which skips
the model's save hook. Story criterion 5 says only `estado` may change.
- A (recommended): one model hook that sets `fechaActualizacion` on every
  `findByIdAndUpdate` of an opportunity. Fixes the order for all three paths,
  including the WhatsApp agent's updates. Criterion 5 reads "only `estado`,
  plus the update date".
- B: this endpoint sets `fechaActualizacion` itself; the agent's updates and
  new activities still leave the date unchanged, so the list order stays
  partly wrong.
- C: leave the date alone; the 2.1 ordering issue stays open.

## Request and responses
```
PATCH /api/v1/crm/oportunidades/:id/estado
{ "estado": "Propuesta" }
200 { …the opportunity in the 2.2 detail shape, with the new estado… }
400 { "error": "Estado no válido. Usa uno de: Prospecto, Calificado, …" }
400 { "error": "El id de la oportunidad no tiene un formato válido." }
404 { "error": "Oportunidad no encontrada." }
500 { "error": "No se pudo actualizar la oportunidad." }
```

## Files affected
- `src/routes/crmRoutes.ts`: `PATCH /oportunidades/:id/estado`, validating the
  id and the stage before calling `actualizarOportunidad(id, { estado })`.
- `src/models/oportunidadModel.ts` (option A): a `findOneAndUpdate` hook that
  sets `fechaActualizacion`.
- `src/services/crmService.ts`: exported `ESTADOS_OPORTUNIDAD` (the seven
  stages, read from the model so they cannot drift); `actualizarOportunidad`
  itself unchanged.
- `src/routes/crmRoutes.test.ts`, `src/services/crmService.test.ts`, and
  `src/models/oportunidadModel.test.ts` (new, option A): tests.
- `CLAUDE.md`: the endpoint, and (option A) the update-date fix in the 2.1
  entry.
- `docs/plans/2.3-plan.md`; `docs/releases/2026-10-09-2.2-merge.md`.

## Tests
- Criterion 1 [BOTH]: route test calls `actualizarOportunidad` with exactly
  `{ estado }` and returns 200 with the re-read opportunity. Live: change,
  then `GET /oportunidades/:id` shows it.
- Criterion 2 [BOTH]: route tests for a wrong value, a wrong accent or case
  (`negociacion`), a missing `estado` and a non-text value: 400, service never
  called. Live call.
- Criterion 3 [BOTH]: service returns `null`; route gives 404. Live call.
- Criterion 4 [BOTH]: malformed id: 400, service never called. Live call.
- Criterion 5 [BOTH]: the route passes only `{ estado }`; extra fields in the
  body (`nombre`, `valorEstimado`) are ignored, checked by a test; live read-back
  shows other fields unchanged.
- Criterion 6 [UAT]: path and Spanish names.

## Risks
- Option A changes the WhatsApp agent's data writes: its opportunity updates
  will now refresh the update date. That is the correct behaviour, but it is a
  change to the agent's path; johpaz should see it in the PR.
- Live testing changes the stage of a "Prueba UAT 2.1" opportunity (test data,
  cleaned in 5.1).
- PATCH from the browser needs the CORS preflight to allow it; checked live.

## Decisions
- `PATCH /oportunidades/:id/estado` with `{ "estado": … }` (story default).
- Stages must match exactly, accents and capitals included (the 2026-07-07
  enum decision: the frontend uses the backend's values verbatim); the error
  lists the seven.
- Validation lives in the route, not in `actualizarOportunidad`, so the
  agent's tool is unchanged (story caveat).
- The response is the opportunity re-read in the 2.2 detail shape, so the UI
  gets the same fields it already uses.
