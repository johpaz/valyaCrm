## Endpoint design

`POST /api/v1/crm/vendedores/identificar`

Request body: `{ "telefono": "+573001234567" }`
Success response (200): `{ "vendedorId": "<db id>", "nombre": "...", "rol": "vendedor" }`

A POST with a body rather than a GET query parameter, for two reasons: a `+` in a
URL query string is conventionally decoded as a space and would break the exact
match, and a phone number is personal data that should not land in server access
logs, browser history or referrer headers. This is how phone identification is
done conventionally (E.164 in a request body). The stored format stays E.164
(`+<countrycode><number>`) per decision #1 — unchanged.

## Implementation steps

### Step 1 — Add `rol` to the phone-matching query

The existing method asks MongoDB for only the name and email. It needs the role
too, or the endpoint cannot return it.

This method is also used by the live WhatsApp path (`conversationService` and
`vendorExperienceService`). I checked both: each passes the returned object
straight through without inspecting its fields, so asking for one extra field
cannot change their behaviour. The `Vendedor` TypeScript type already declares
`rol`, so no type definition changes.

- Files touched: `src/services/crmService.ts`
- Verify: `bun run lint` passes and the project type-checks. Behaviour is confirmed
  in Step 3.

### Step 2 — Add the endpoint

Add `POST /vendedores/identificar` to the CRM route file, following the pattern the
existing routes already use (returning a `Response` with an explicit status code).

Behaviour:
- Reads `telefono` from the request body.
- Missing, empty, or not a string → HTTP 400, clear Spanish message.
- Otherwise calls `buscarVendedorPorTelefono`. That method already matches exactly
  and already excludes inactive reps, so inactive reps return as "not found" with
  no extra work.
- No match → HTTP 404, clear "not found" message.
- Match → HTTP 200 with `vendedorId`, `nombre`, `rol`. Email is deliberately not
  returned; the brief specifies these three fields.
- Unexpected error → HTTP 500, logged, matching the existing error style. The
  service method has no error handling of its own, so the route wraps the call.

- Files touched: `src/routes/crmRoutes.ts`
- Verify: `bun run lint` passes; the server starts without error.

## Risks and unknowns

1. **No automated tests exist in this repo.** Everything is verified by hand, so
   there is no regression safety net on the WhatsApp path. The change to the shared
   service method is additive and both callers were checked by reading, which is
   weaker than test cover. Build-plan open question 8 (whether to invest in tests)
   is still open and is a PM decision. My recommendation: proceed without tests on
   this ticket, and decide the testing approach as its own ticket before the
   remaining 19 — `bun test` is already wired up and Bun has a built-in runner, so
   the cost is in deciding how tests reach MongoDB, not in installing tooling.

2. **Phone numbers already in the database may not be in E.164 format.** Flagged in
   the brief as data hygiene. Does not block building, but an existing rep could
   fail to be identified for data reasons rather than code reasons — worth knowing
   before concluding the endpoint is broken.

3. **Test reps will remain in the database** unless removed. They are obvious
   throwaways, but they are real records in the same database the WhatsApp agent
   reads. Worth deciding at the end of the ticket whether to leave or delete them.

## Open questions

None blocking. The two earlier questions (whether a testable rep exists, and
whether an inactive rep exists) are resolved: both are created via the existing

## Deferred — recorded so nothing is lost

These came out of planning this ticket and belong elsewhere:

1. **Country picker on phone entry (PM decision, 2026-10-02).** Phone numbers are
   entered via a country picker plus local digits, assembled into E.164. This
   applies to the frontend entry screen (`Ingreso`) and the admin dashboard's
   add-salesperson form — not to this backend ticket. It partly answers build-plan
   non-blocking open question 6 (`Ingreso` entry UX: the rep types their number,
   with a picker, rather than choosing from a list of reps). Should be written into
   those two briefs.
2. **Fix the three buggy `/crm/.../buscar` endpoints.** They pass an empty
   `vendedorId`. Fixing them requires the caller to supply a real `vendedorId` —
   which is what this ticket's endpoint provides, so they depend on this landing
   first. Worth its own ticket; not currently in the build plan.
3. **Phone-number normalisation before matching** (trim, strip dashes and brackets,
   re-add a missing `+`). Would make matching robust against messy data. Beyond the
   brief, which fixes matching as an exact comparison. Worth its own ticket.
4. **Salesperson password field blocks the admin dashboard ticket.** The
   salesperson model requires `contrasena`, so a salesperson cannot be saved
   without one — but the beta decided against passwords (decision #1), nothing in
   the backend reads the field, and no password-checking code or hashing library
   exists. It dates from the repo's first commit, alongside a stubbed
   "simulate authentication" function, and went unnoticed because nothing had ever
   created a salesperson. PM decision (2026-10-02): the password is **not**
   surfaced in the UI. The backend must therefore stop requiring it —
   recommended fix is dropping `required: true` on the model (one line,
   validation-only, no stored data affected) rather than having the backend invent
   a dummy value. Consequence for the build plan: "Admin dashboard — add
   salesperson" is no longer a frontend-only ticket, and the model change is the
   backend developer's to agree.

5. **CLAUDE.md MongoDB verification command** references `mongosh`, which is not
   installed on this machine. Documentation correction for a later docs pass.
