Plan: Get one opportunity by id
ID: 2.2
Date: 2026-10-09
Round: 1
Goal: Add `GET /api/v1/crm/oportunidades/:id`, returning one opportunity with
its company, contact, product and activities, so the detail screen (2.7) can
show the deal the rep tapped.

## Out of scope
- Wiring the detail screen (2.7); stage update (2.3).
- Checking that the opportunity belongs to the logged-in rep (story: arrives
  with real auth); authentication.

## Response shape
```
200 { …the same fields as each item of GET /oportunidades (2.1)…,
      "actividades": [
        { "_id", "nombre", "tipo", "descripcion", "estado", "prioridad",
          "fechaProgramada", "fechaLimite" }
      ] }
400 { "error": "El id de la oportunidad no tiene un formato válido." }
404 { "error": "Oportunidad no encontrada." }
500 { "error": "No se pudo obtener la oportunidad." }
```

## Files affected
- `src/services/crmService.ts`: new `obtenerOportunidadPorId(id)` (returns
  `null` when not found), reusing 2.1's `darFormaOportunidad` plus the
  activities.
- `src/routes/crmRoutes.ts`: `GET /oportunidades/:id`.
- `src/services/crmService.test.ts`, `src/routes/crmRoutes.test.ts`: tests.
- `CLAUDE.md`: the endpoint under "Current API endpoints".
- `docs/plans/2.2-plan.md`; `docs/releases/2026-10-09-2.1-merge.md`.

## Steps
Step 1: tests, then the service method · verify: `bun test` passes.
Step 2: tests, then the route · verify: `bun test` passes.
Step 3: live check with the "Prueba UAT 2.1 Oportunidad completa" plus two
test activities on it ("Prueba UAT 2.2 …", for 5.1), a made-up id and a
malformed id; then `CLAUDE.md` · verify: 200 with company, contact, product and
both activities; 404; 400.

## Tests
- Criterion 1 [BOTH]: service test checks the lookup by id populates company,
  contact, product and activities (with exact field lists) and shapes the
  result; route test returns 200 with it. Live call.
- Criterion 2 [BOTH]: service returns `null` when not found; route turns that
  into 404 with the message. Live call with a made-up id.
- Criterion 3 [BOTH]: route test: a malformed id gets 400 without touching the
  database; also a 500 with a generic message on a database failure. Live call.
- Criterion 4 [UAT]: path and Spanish names, in your checklist.

## Risks
- The live check adds two "Prueba UAT 2.2 …" activities to the test
  opportunity (cleaned in 5.1). Scripts use the database name set in code
  (`crm_vendedor_b2b`), per the 2.1 lesson.
- The 20-cap and ordering issues from 2.1 don't apply: this fetches one
  opportunity by id.

## Decisions
- Path parameter `/oportunidades/:id` (story default); it does not clash with
  `/oportunidades/buscar`, which Elysia matches as a fixed path first (checked
  by a test).
- Same item shape as the 2.1 list plus `actividades`, so 2.6 and 2.7 share one
  mapping on the frontend.
- Activities come with this call (story default), soonest `fechaProgramada`
  first; deleted or unpopulated activity ids are left out.
- Malformed id is caught before the database (24-character hex check), so it
  is a 400, never a cast-error 500.
- Merge records for backend features now go in `valyaCrm/docs/releases/`
  (each repo carries its own `docs/releases/`), committed with the backend
  branch, instead of a separate `valya_front` docs PR.
